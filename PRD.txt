# E-Commerce REST API

## Product Requirements Document (PRD)

**Version:** 1.0
**Status:** Planning
**Backend:** Laravel
**Database:** MySQL
**API Style:** RESTful API
**Authentication:** Token-based Authentication
**Primary Goal:** Build a production-style E-Commerce Backend suitable for a professional Laravel Backend Developer portfolio.

---

# 1. Product Overview

## 1.1 Project Idea

The project is a complete E-Commerce backend that provides RESTful APIs for managing an online store.

The system will support customers who want to browse products, manage their carts, place orders, and track them.

It will also provide administrative functionality for managing products, inventory, customers, orders, discounts, and other store operations.

The project will be built as a **backend-first REST API**, without depending on a web frontend.

---

# 2. Problem Statement

Small and medium-sized online stores need a backend system that can:

* Manage products and categories.
* Track inventory.
* Allow customers to create carts and orders.
* Manage customer accounts and addresses.
* Handle discounts and coupons.
* Process the order lifecycle.
* Provide administrative controls.
* Notify users about important events.
* Maintain reliable and secure business logic.

The goal is to design and implement these requirements using Laravel in a way that resembles a real-world production application.

---

The project should demonstrate the ability to:

1. Build a RESTful API with Laravel.

# 4. Target Users

The system has three primary user types.

## 4.1 Customer

A normal store user who can:

* Register and log in.
* Browse products.
* Search and filter products.
* Manage their profile.
* Manage addresses.
* Add products to a cart.
* Manage wishlist items.
* Create orders.
* Apply coupons.
* View order history.
* Track order status.
* Leave reviews and ratings.

---

## 4.2 Admin

The administrator manages the entire store.

Admin capabilities include:

* Manage users.
* Manage products.
* Manage categories.
* Manage brands.
* Manage product variants.
* Manage inventory.
* Manage coupons.
* Manage orders.
* Manage reviews.
* View reports and statistics.

---

## 4.3 System

Some operations should be performed automatically by the application.

Examples:

* Sending notifications.
* Processing queued jobs.
* Detecting low-stock products.
* Expiring coupons.
* Escalating or handling failed operations.
* Cleaning temporary data.
* Recording important system events.

# 5. Core Features

## 5.1 Authentication

The API must support:

* User registration.
* Login.
* Logout.
* Current authenticated user.
* Password hashing.
* Password reset.
* Email verification.
* Token-based authentication.

Authentication must be separated from authorization.

---

# 5.2 User Management

Customers should be able to:

* View their profile.
* Update profile information.
* Change password.
* Manage addresses.

Admins should be able to:

* View users.
* Search users.
* Filter users.
* Activate/deactivate accounts where appropriate.

---

# 5.3 Product Catalog

The system must support:

### Products

Each product may contain:

* Name
* Slug
* Description
* Short description
* SKU
* Price
* Discount price
* Status
* Category
* Brand
* Images
* Stock information

### Categories

Products can belong to categories.

Categories should support hierarchical organization where appropriate.

Example:

```text
Electronics
├── Phones
├── Laptops
└── Accessories
```

### Brands

Products may belong to brands.

### Product Variants

Products may have variants such as:

```text
T-Shirt
├── Size: S
├── Size: M
├── Size: L
└── Size: XL
```

or:

```text
Laptop
├── RAM: 8GB
├── RAM: 16GB
└── RAM: 32GB
```

---

# 5.4 Product Images

The API must support product image management.

Requirements include:

* Upload image.
* Delete image.
* Associate images with products.
* Define a primary image.
* Validate uploaded files.
* Prevent unsafe file uploads.

---

# 5.5 Product Listing

Customers should be able to:

* Retrieve products.
* Retrieve a single product.
* Search by keyword.
* Filter by category.
* Filter by brand.
* Filter by price range.
* Sort products.
* Paginate results.

Example:

```text
GET /api/products
GET /api/products/{product}
```

---

# 5.6 Inventory Management

The system must track product stock.

Requirements:

* Add stock.
* Remove stock.
* View current stock.
* Detect insufficient stock.
* Prevent ordering unavailable quantities.
* Track stock changes.
* Identify low-stock products.

Inventory updates must maintain database consistency.

---

# 5.7 Cart

Customers can:

* Create/use a cart.
* Add products.
* Update quantities.
* Remove products.
* View cart.
* Clear cart.

Business rules include:

* Quantity must be valid.
* Product must be available.
* Requested quantity must not exceed available stock.
* Cart totals must be calculated reliably.

---

# 5.8 Wishlist

Customers can:

* Add a product to wishlist.
* Remove a product.
* View wishlist.

A customer should not have duplicate wishlist entries for the same product.

---

# 5.9 Addresses

Customers can manage shipping addresses.

An address may contain:

* Full name
* Phone
* Country
* City
* Area
* Street
* Building
* Postal code
* Additional information

A customer can have multiple addresses and designate one as the default address.

---

# 5.10 Coupons and Discounts

The system should support coupons.

A coupon may contain:

* Code
* Type
* Value
* Minimum order amount
* Maximum discount
* Usage limit
* Per-user usage limit
* Start date
* Expiration date
* Active status

Coupon types may include:

```text
Percentage
Fixed Amount
```

The system must validate coupon eligibility before applying a discount.

---

# 5.11 Orders

Customers can create orders from their cart.

An order should contain:

* Order number
* Customer
* Shipping address snapshot
* Items
* Quantities
* Prices
* Discounts
* Shipping cost
* Total
* Payment status
* Order status
* Timestamps

Example lifecycle:

```text
Pending
   ↓
Confirmed
   ↓
Processing
   ↓
Shipped
   ↓
Delivered
```

Possible alternative outcomes:

```text
Pending → Cancelled
Confirmed → Cancelled
Processing → Cancelled
```

The exact allowed transitions must be enforced by business rules.

---

# 5.12 Order Items

Each order contains one or more order items.

Each item should preserve the price at the time the order was created.

This is important because product prices may change later.

Example:

```text
Product current price: $150

Order created:
Order Item price: $130
```

The historical order must continue showing `$130`.

---

# 5.13 Payments

The first version will implement a **payment simulation layer** rather than connecting to a real payment provider.

The system should support:

* Payment creation.
* Payment status.
* Payment reference.
* Successful payment simulation.
* Failed payment simulation.
* Refund simulation where appropriate.

The architecture should allow a real payment gateway to be integrated later.

---

# 5.14 Reviews and Ratings

Customers who purchased a product may submit:

* Rating
* Review title
* Review body

Business rules:

* Rating must be within the allowed range.
* A customer should only review according to the defined purchase policy.
* Duplicate reviews should be controlled.
* Reviews can be moderated by admins.

---

# 5.15 Notifications

The system should notify users about important events.

Examples:

* Account verification.
* Password reset.
* Order created.
* Order confirmed.
* Order shipped.
* Order delivered.
* Payment failure.

Notifications may be handled asynchronously using queues.

Product endpoints must support:

### Search

```text

```

### Filtering

```text

?brand=apple
?min_price=500
```

### Sorting

```text

```

### Pagination

```text
?page=2&per_page=20
```

The API should return pagination metadata.

# 5.17 Admin Dashboard API

The backend should provide administrative statistics such as:

* Total users.
* Total products.
* Total orders.
* Total revenue.
* Pending orders.
* Low-stock products.
* Top-selling products.

These will be exposed through API endpoints rather than a frontend dashboard.

# 6. Authorization

The application must distinguish between authentication and authorization.

Examples:

```text
Customer
    ↓
Can view own orders

Admin
    ↓
Can view/manage all orders
```

Customers must not be able to modify another customer's resources.

Authorization should use Laravel's appropriate mechanisms such as:

* Policies
* Gates
* Middleware
* Role/permission checks

---

# 7. Business Rules

Important business rules include:

### Product

* SKU must be unique.
* Product price cannot be invalid.
* Product must be active to be purchasable.
* Product must have sufficient stock.

### Cart

* Quantity must be greater than zero.
* Duplicate cart items should be handled correctly.
* Out-of-stock products cannot be purchased.

### Orders

* Empty carts cannot create orders.
* Stock must be checked before order creation.
* Order creation must be atomic.
* Order items must preserve their historical prices.
* Inventory must be updated consistently.

### Coupons

* Expired coupons cannot be used.
* Inactive coupons cannot be used.
* Usage limits must be enforced.
* Minimum order requirements must be enforced.

### Reviews

* Review rules must be enforced at the API/business-logic level.
* Users must not be allowed to manipulate another user's review.

---

# 8. Transactions and Data Consistency

Operations involving multiple related database changes should use database transactions where necessary.

Example:

```text
Create Order
    ↓
Create Order Items
    ↓
Decrease Inventory
    ↓
Apply Coupon Usage
    ↓
Clear Cart
    ↓
Commit
```

If an important operation fails:

```text
Rollback
```

The system must avoid partially completed orders.

---

# 9. Performance Requirements

The API should consider:

* Database indexing.
* Eager loading.
* Avoiding N+1 queries.
* Pagination.
* Query optimization.
* Caching frequently accessed data.
* Queueing expensive operations.
* Proper API response structure.

Performance decisions should be based on actual application needs rather than blindly applying patterns.

The API must follow secure backend practices.

Areas include:

* Authentication.
* Authorization.
* Request validation.
* SQL injection prevention.
* Mass assignment protection.
* Secure file upload validation.
* Rate limiting.
* Sensitive data protection.
* Secure password handling.
* Proper error responses.
* Preventing unauthorized resource access.

# 11. API Design Requirements

The API should follow RESTful conventions.

Example:

```text
GET    /api/products
GET    /api/products/{id}

POST   /api/products

PUT    /api/products/{id}
PATCH  /api/products/{id}

DELETE /api/products/{id}
```

Endpoints should:

* Use appropriate HTTP methods.
* Return appropriate HTTP status codes.
* Validate input.
* Return consistent JSON responses.
* Return meaningful error messages.
* Use API Resources where appropriate.
* Support pagination for collection endpoints.

---

# 12. Error Handling

The API should return consistent error responses.

Example:

```json
{
    "success": false,
    "message": "The requested product is unavailable.",
    "errors": {}
}
```

Validation errors should provide structured information.

The application should avoid exposing internal implementation details in production error responses.
